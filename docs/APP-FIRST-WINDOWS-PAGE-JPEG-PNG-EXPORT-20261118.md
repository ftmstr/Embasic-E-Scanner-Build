## User-facing behavior
Each Windows WinUI3 workspace page has **JPG dışa aktar** and **PNG dışa aktar** buttons. The OS `FileSavePicker` supplies a local filesystem target only; blank/virtual/cloud-only paths fail closed. Each action rehashes the page's original private file and rejects changed bytes before decoding. It uses native `BitmapDecoder` with EXIF orientation, the existing CPU four-corner perspective geometry, then clockwise 0/90/180/270 degrees. JPEG alpha is composited on opaque white; PNG preserves straight alpha. The pure `PageImageOutputPlan` admits only `.jpg/image/jpeg` or `.png/image/png`, 24 MP and 8000px/edge source bounds and valid quad/rotation. Bounded non-destructive transforms apply to export only, not stored originals. JPEG encoder explicitly requests ImageQuality 0.92 (Android requests 92/100); actual codec quality behavior, output visual equivalence, and color/ICC are **NOT VERIFIED**.

## Staging / target semantics
The encoder writes a unique `.embasic-image-<UUID>.tmp` directly beside the destination. Before publishing, the stage is fully closed and read back: 16-byte-or-larger payload; <=256 MiB; format signature, WinRT BitmapDecoder MIME plus exact oriented dimensions, and readable SHA-256. Reparse-point destination, original-as-destination, incompatible extension, unsafe source pixels and corrupt encoder output are rejected. Finally `File.Move(stage,target,overwrite:true)` publishes on the same volume, with no copy fallback; a codec/validation failure before the move does not intentionally overwrite an existing target. Stage cleanup happens in `finally`. This is **not** a proven power-loss durable atomic replacement or FileSavePicker provider-level rollback. There is no post-publish fsync or on-device reopen benchmark. Existing JPEG/PNG cloud-provider fallback is **not implemented**.
